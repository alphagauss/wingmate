# 运行时维护指南

用于调整 DSH 版本、发行依赖、裁剪与压缩规则，以及集成社区或自用插件。这里保存选择依据和维护责任；脚本表达具体步骤，配置和锁文件保存精确版本。

## 来源与版本

当前从官方 npm 发布包获取 DSH，不从参考仓库复制编译产物。发行依赖声明以 [runtime/package.json](../runtime/package.json) 为准，依赖解析结果以其 [锁文件](../runtime/package-lock.json) 为准。

准备 DSH 运行包时默认通过 `https://registry.npmmirror.com/` 获取 npm 发布包，并按锁文件校验完整性。需要切回官方源时，在构建环境中设置 `npm_config_registry=https://registry.npmjs.org/`。已有运行包命中构建缓存时会直接复用。安装阶段会显示所选源，并在交互终端单行更新 npm 下载请求和缓存检查的次数，重定向输出时定期打印摘要。设置 `npm_config_loglevel=http` 可查看 npm 的逐请求日志。

一次发行需要能对应到明确的上游版本与依赖内容。以后即使支持“拉取最新 tag”，也应先选定并记录具体版本，再准备发行包；不把漂移的 `latest` 当作已确定版本，也不在用户每次启动时重新选择上游。

改用源码构建或社区 fork 时，记录来源 URL、tag 对应的提交及必要补丁。正式发行不能只依赖被忽略的上游工作副本。来源改变不自动意味着接受该来源新增的默认功能或行为。

## 打包范围与所有权

无 GUI 的 `wingmate` 发行入口并列携带独立管理服务、所选 DSH 及其运行依赖，桌面构建另带桌面组件，系统前提见 [项目入口](../README.md#使用)。当前 Node 由系统提供，Zstd 解压能力随应用交付。用户凭据、会话、个人设置、开发缓存不属于预装运行内容。

在目标系统和处理器架构上本机构建。准备阶段核对 Node 与 Rust 主机目标，并按 Node 平台和架构安装、裁剪依赖。Cargo 只内嵌与目标一致的归档。发行前在对应平台和架构用单文件产物验收，原生依赖覆盖范围以锁文件及实际结果为准。

当前锁文件中的 Sherpa-ONNX 缺少 Windows ARM64 原生包。该组合要作为保留语音能力的完整发行，需先补齐并验收原生依赖。

新增组件需要明确它属于“随包提供”“使用系统安装”还是“用户按需安装/下载”，以及是否增加了使用前提。组件名称和版本放在实际依赖声明中，文档记录为什么加入，不维护第二份版本清单。

生成内容统一放在 `work`。原始 npm 安装树位于 `work/cache/runtime-dependencies/<依赖指纹>`，npm 下载缓存位于 `work/cache/npm`。发行组件位于 `work/build/runtime`，开发组件位于 `work/dev/components`。Rust 二进制继续构建到 `target`，发行引导直接使用这些编译产物，不另建暂存副本。`runtime` 只保存受版本管理的声明、锁文件、补丁与控制代码。

`pnpm runtime:dev` 和 `pnpm runtime:prepare` 共用按依赖声明、锁文件、目标平台和安装规则确定的原始安装缓存。插件或补丁变化不触发 `npm ci`。两种模式分别准备 DSH 基础包、各预装插件、代码补丁和启动配置的归档及清单。开发归档保留完整依赖，发行归档按下方规则裁剪。生成目录由工具管理，修改通过源文件进入。

先显式执行插件自己的 `build`（存在时），再用 `npm pack --ignore-scripts` 打包。插件负责产出自足的编译资源，解开插件包不安装其依赖。新插件需加入构建清单和启动配置。各组件分别判断缓存，基础包不受插件内容、启动配置和补丁文本变化影响。代码补丁在构建时对原始文件校验并生成最终文件，基础包排除由补丁包提供的路径。

准备命令通过发行入口的小型构建工具执行，以操作系统文件锁串行化插件构建和归档写入。开发准备与后台启停、旧目录回收共用操作锁。准备发布归档和目标清单，并构建独立服务。后台使用中的目录由启动流程在停机后更新。

每个预装插件的实际 `.tgz` 会先在临时目录解包检查，再参与缓存判断与组装。检查覆盖 DSH 兼容版本、宿主入口、声明的客户端入口及各配置补丁文件。文件预览插件同时按资源清单校验归档内的离线资源。宿主模块由独立 Node 进程导入，关闭全局模块搜索及 `NODE_PATH`、`NODE_OPTIONS` 注入，避免开发环境补足遗漏。插件激活及浏览器行为由运行时验证覆盖。

当前预装插件要求运行产物自足，声明非空 `dependencies`、`optionalDependencies` 或 `peerDependencies` 会使检查失败，即使当前 DSH 安装树碰巧包含同名包。需要外部运行依赖时先实现明确的依赖部署和验证，再放开此约束。构建期 `devDependencies` 和客户端通过 DSH 模块系统共享的依赖沿用各自声明。

`pnpm build` 先准备运行归档并构建独立服务，再构建桌面，最后构建携带这些并列组件的发行入口。`pnpm build --headless` 跳过桌面及其系统构建前提。服务自身不携带 DSH 归档或解压依赖；桌面只携带运行清单元数据，资源仅在外层发行入口保存一份。服务构建不反向依赖发行入口或桌面，避免嵌套归档和构建循环。

## 去重与精简取舍

| 当前选择 | 原因与保留边界 | 升级时重新判断 |
| --- | --- | --- |
| 将 Zod、debug、ms 的共享版本固定在运行时顶层 | 避免多个依赖重复嵌套同版本；保持上游声明的兼容范围，不使用强制 overrides 消除版本冲突 | 上游是否仍有重复；现有固定是否仍兼容；必要时调整或撤销额外固定，允许不兼容版本并存 |
| 排除 source map、PDB 等调试元数据 | 优先缩小发行体积，接受发行包中调试映射与符号信息减少；安装树仍保留 | 这些文件是否开始参与运行功能或新的调试交付需求 |
| 排除明确的异系统/异架构预编译文件 | 当前发行只需要目标平台代码；不能根据不认识的文件名猜测用途 | 上游平台命名和目录结构是否变化；目标架构与兼容后备实现是否被误排除 |
| 保留类型声明、TypeScript 源码、许可证及相关声明 | 兼顾插件开发、包的实际入口与分发义务，不用扩展名一刀切 | 新依赖的导出、加载方式和许可要求是否改变 |
| 用 File Viewer 替换 Word、PowerPoint 侧栏预览，移除所有平台的 LibreOffice Kit 运行内容及 WASM 后备引擎 | 以浏览器预览降低分发体积并扩展格式；禁用 `office-to-pdf` 并移除旧预览注册，保留许可证与声明。Office skill 未启用，后台 Office 转 PDF、渲染和重算不属于当前发行能力 | 新增消费者是否需要 LibreOffice，预览版式能否满足需求；恢复引擎时必须同步调整组合、补丁及验证 |
| 保留图片、语音、Web 及其他现有 WASM 内容 | 保留已选择的功能与非 Office 后备实现 | 功能依赖是否变化；不能仅凭某次未调用就认定不需要 |

精确文件规则以 [裁剪规则](../scripts/runtime-files.mjs) 为准。未知内容先保留；许可证优先于裁剪。依赖升级后重新审视规则，不把某一版安装布局固化为永久前提。

## 压缩选择

发行组件使用 Node 内置的 Zstd 9。开发组件使用 Zstd 1，优先缩短本地准备时间。解压库随应用交付，构建和运行无需额外安装压缩工具。输入和归档指纹均一致时复用该组件。`pnpm runtime:benchmark` 默认比较发行基础包。

调整格式或参数时，对同一份内容比较体积、构建成本、解压成本与额外工具要求。纯解压耗时不等于首次启动耗时，算法对比也不能代替发行产物的释放测试。测量属于有日期的证据，不作为永久体积或时延承诺，见[首次压缩对比记录](records/2026-11-05-runtime-size.md)。

## 释放与复用

发行引导持 `bootstrap.lock` 协调组件发布。服务和桌面分别释放到管理目录的 `services/<指纹前 6 位>` 与 `desktops/<指纹前 6 位>`。开发服务也运行释放副本。组件先写临时目录，再完整发布。复用目录时校验完整 SHA-256，前缀相同而内容不同时报告冲突。打开新版发行入口会启动对应桌面副本，并在其登记使用后回收已退出的旧桌面副本。

启动优先复用已运行且协议兼容的服务。执行「重启并更新」或 `wingmate restart` 时，发行入口先停止当前 DSH。服务指纹有变化时，再退出旧服务并等待运行锁释放，准备组件后由目标服务启动 DSH。管理服务的本机发现、认证和 `/rpc` 的 `status`、`stop`、`shutdown` 是跨版本的升级接口。业务已停止时，可用 `service-restart` 单独切换服务，确认新服务就绪后回收旧受管服务目录。

发行入口负责以下业务组件的安装和回收，与服务启停共用 `operation.lock`。安装完成后原子发布 `runtime.json`，记录已安装目录、清单指纹、Node 路径与数据目录。管理服务只读取并校验这些内容，因此业务停止后可以在没有发行入口或客户端进程参与时再次启动。缺少或损坏的运行内容需由发行入口修复，不由服务自行释放。

开发和发行的安装目录均位于各自的[管理目录](../crates/wingmate-service/README.md#数据与管理边界)下，命名为 `runtimes/dsh-<固定版本>-<基础包 SHA-256 前 6 位>`。`.wingmate-base` 记录完整基础包指纹，`installed.json` 记录实际安装的组件及完整指纹。遇到同名目录且无法确认归属时，启动会报错，请检查并手动移走占用路径后重试。

构建时用整份目标清单生成运行指纹，用于现有版本提示和后台身份核对。打开新版时，正在运行的后台继续使用原文件。同一 DSH 版本下，发行入口在明确更新或准备启动已停止的后台时比较安装清单并替换变化的组件。插件按固定名称整个目录替换，旧内容先改名移入待清理目录。无需遍历和重新校验全部运行文件。文件损坏时，在后台停止后删除相应运行目录再启动。

基础包变化时使用新运行目录。补丁内容变化但目标文件集合不变时，只替换补丁文件。新增或撤销补丁导致文件归属变化时使用新基础包。每个发行文件只在其所属组件中保存一份。被补丁替换的原始文件仅留在构建用的 npm 安装缓存中。

首次释放在临时目录完成后发布。增量安装在替换前移除安装清单，安装完成后重新发布。若中断，后续启动在确认后台停止后重新释放缺少清单的受管目录。启动失败可修复后重试，或停止后台后删除运行目录并重装。

确认目标管理服务与 DSH 的身份、指纹和就绪状态后，发行入口才回收旧服务副本、待清理内容和旧基础运行目录。桌面通过引导事件先打开工作台，清理在引导进程中继续。命令行启动和重启等待清理结束。清理失败时记录原因，下次成功启动或连接同版后台时重试。清理仅针对当前布局的受管内容。会话、设置和凭据独立存放。

## 升级时需要作出的判断

| 环节 | 需要确认并留下的结论 |
| --- | --- |
| 选择版本 | 获取来源及具体版本；上游变更是否改变 Node 前提、配置/数据兼容性、插件机制或默认行为 |
| 更新依赖 | 锁文件变化是否符合本次升级范围；额外顶层固定还有没有必要；有无新增原生库、下载步骤或系统依赖 |
| 调整适配 | 现有补丁和裁剪是否仍适用；上游已解决的问题是否可以撤销本地适配；是否引入行为差异 |
| 准备发行 | 是否仍能从受管理的输入准备单文件产物；新内容如何影响首次释放及已有版本目录 |
| 验证与交付 | 哪些能力受影响、做了哪些验证、还有哪些未验证；旧后台和既有数据如何继续使用或切换 |

验证入口在 [根 README](../README.md#开发入口)。DSH 升级及打包、释放或裁剪变更按[发行版验证条件](../scripts/README.md#验证边界)覆盖实际单文件释放、Web 连接、后台管理及受影响的原生组件。压缩参数变化也需检查解压内容一致和真实启动。

涉及插件加载、安装或配置变更，补充对应插件验证；涉及 Node 前提、系统或架构变化，针对目标环境验证。涉及数据格式变化，先使用隔离副本验证兼容性，不拿日常会话作为试验数据。

记录能力边界：语音库加载不等于模型推理通过，Web 打开不等于真实模型调用通过，Office 转换用例通过也不代表所有格式都已覆盖。具体验证原则见 [验证约定](../scripts/README.md)。

## 社区和自用插件集成

当前预装 [Wingmate 后台服务](../plugins/wingmate-web/README.md)、[文件预览](../plugins/wingmate-file-viewer/README.md)和[执行后端](../plugins/wingmate-backends/README.md)。构建脚本明确指定预装哪些包，[启动补丁](../plugins/cordis.patch.yml)决定 Wingmate 启动 Web 时默认启用哪些插件。开发版和发行版均随运行包携带这份补丁，并将它计入构建指纹。参考仓库、本地开发插件、发行预装组件是不同状态，创建目录或加入开发 workspace 不会自动改变发行内容。

执行后端插件内联 ACP SDK，并携带锁定版本的 Codex ACP 适配器。Agent 的主机依赖见[插件文档](../plugins/wingmate-backends/README.md#主机依赖)。选择 Codex 或检查连接时才启动适配器，缺少 Agent 不影响 DSH 启动。构建和发行使用依赖声明与锁文件中的适配器发布包。

第一次实际集成时建立简短记录：本项目维护的插件写在所属 `plugins/<名称>/README.md`；仅消费外部发布包的组件写在 `docs/integrations/<名称>.md`。后者目录在实际需要时创建。记录包含：

| 内容 | 要说明的问题 |
| --- | --- |
| 目的与来源 | 为什么集成、提供什么能力、上游地址；精确版本以哪个声明/锁文件为准 |
| 许可与发行 | 是否允许所选分发方式，需要保留什么声明；是否随包提供及是否默认启用 |
| 兼容与依赖 | 适配的 DSH 范围、Node/原生/系统依赖，有无额外下载和用户配置要求 |
| 客户端能力 | Web、TUI、移动端分别是已验证、未验证还是不支持；后端加载不能替代界面验证 |
| 本地适配 | 是否改动上游，改动原因、对应问题/提交、升级检查点和撤销条件 |
| 验收与退出 | 验证哪些用户可见能力；移除或禁用后配置、数据和已有工作流会怎样 |

预装和默认启用要分别决定；不携带个人凭据，不无记录地覆盖用户已有配置。开发目录中的插件要先形成可安装产物，再接入发行依赖，不依赖工作区链接。

各预装插件独立进入组件清单，整份清单决定运行指纹。

## 适配与升级记录

代码补丁保存在 `runtime/patches/dsh-<版本>.json`，按数组顺序在构建阶段生成最终文件。每项记录包版本、目标文件、原始 SHA-256、唯一匹配的替换内容及对应源码链接。版本、文件哈希或匹配次数不符时构建失败；升级 DSH 时需审查并提供对应版本清单，无补丁时显式使用空数组。补丁不直接修改已有运行目录，也不依赖本机 Git 命令。

配置组合优先使用 DSH 的 patch 和插件接口；代码补丁用于上游尚无扩展点的必要改动，原因和撤销条件放在对应插件文档。以后需要源码构建时，先从受管理的 URL、tag 与 commit 准备干净源码并应用补丁，再把编译包接入运行时组装，不能只修改 `stage` 或被忽略的参考仓库。

实际 DSH 升级、预装组件变化或兼容性调整时，在 `docs/records/` 新增有日期的简短记录：变更目标与前后版本、输入/来源、此次取舍及适配变化、验证环境和结论、已有安装的处理方式、未验证项。只记录发生的工作，不预建空台账。
